# 十个模块的分析规则

这些是分析范围，不是固定二级 Tab 或固定行项目清单。只为本次文件中有依据的主题创建二级 Tab；表头按数据适配。允许在一个模块中使用多种内容块。

| 固定一级 Tab | 分析范围 | 有依据时可采用的动态组织方式 |
| --- | --- | --- |
| 基础信息 | 项目名称/编号、采购人/代理机构、采购方式、采购范围、地点、预算/限价、履约期限、获取文件/递交/开标时间、保证金、付款等 | 依据该文件的项目概况、供应商须知、日程安排、费用和商务条件分组 |
| 技术参数要求 | 标的/分包、型号规格、数量单位、性能阈值、功能、接口、实施、交付、验收、培训、维护；特别标识强制性/星号条款 | 按产品、子系统、包号、技术章节或服务阶段分组；保留单位、比较符和否定词 |
| 潜在风险 | 时间冲突、条款矛盾、预算/成本、交付/验收、合同责任、数据接口、资质时效、报价或评分机制中的履约风险 | 根据实际风险分组；分别列原文事实、风险推断、影响、建议；不要制造泛化风险填满模块 |
| 废标项 | 无效投标/响应、资格或符合性不通过、否决条款、实质性要求、签章/授权/密封/上传、超限价、保证金、串标等 | 按原文资格审查、符合性审查、报价、电子递交等类别分组；逐条保留触发条件，不漏附录中的否决条款 |
| 投标人资格要求 | 主体资格、资质许可证、业绩、财务、信誉、人员、联合体、关联关系及需要的证明 | 按文件实际审查维度分组；区别必须条件、评分加分条件及中标后履约条件 |
| 评标标准 | 评审方法、资格/符合性、价格/商务/技术评分、满分、公式、权重、扣分、并列排名、候选人推荐 | 按实际评审阶段及评分表分组；逐项保留分值/公式，核对总分和边界，不自行补缺失分数 |
| 投标文件要求 | 文件组成、格式、语言、份数、有效期、签字盖章、授权、目录/页码、电子格式/上传、报价及偏离规则 | 按编制、签章、报价、提交要求等实际主题分组；与“所需文件”的具体文件清单区分 |
| 应标所需文件 | 营业执照、资质、授权、业绩、报价清单、技术响应、承诺函等具体提交材料及适用条件 | 根据原文商务/资格/技术/报价/其他附件或包号分组；列原文要求、签章、有效期和适用情况 |
| 投标文件模板 | 文件中的投标函、授权书、报价表、偏离表、承诺函及其他表单样式 | 按真实表单标题建二级 Tab；从原件截取 Word，保持原始版式和待填占位，不填造企业事实；通过 momo-file-editor 预览 |
| 智能问答 | 用户已有问题、带证据的答案；初次解析可依据文件生成少量有实际价值的常见问题 | 按问题主题分组；可为空；不得把检索不到的信息当作肯定答案 |

## 证据与准确性

每条事实行或事实文本块至少有一个证据，包含文件名、PDF 页码或 DOCX 段落/表格位置，以及支持该行的原文摘录。超过一项要求的复杂行可引用多个来源。引用不需要暴露完整源文档预览。

数据使用 `basis`：

- `explicit`：文档明示，必须有证据。
- `inferred`：基于文档推断，必须有证据和解释推断过程的 `note`；页面显示“推断”，不能混成文件明示。
- `missing`：对已检查范围确实未明确的必要字段，给出 `note`；不能用于未读页。未读页应写在 `coverage.unread` 并把状态设为 `partial`。

保留强弱程度：“应/必须/不得”和“可/建议”不能互换；星号、否决项、分包、联合体适用条件均应保留。参数精简不能丢单位、数量、容差、比较关系或例外。

同一文件重复条款可合并，但相似条款存在不同阈值、日期或适用范围时，不得去重抹掉差异。补充文件只有明确说明替换/修改某条款时才采用其修改后的内容，并保留变更出处。

## 文件模板

用户没有提供投标人资料时，保留“[投标人名称]”“[日期]”等待填项。只有文件原有的表单放在“投标文件模板”作为原文模板；AI 建议补充的格式只能在说明文本中显著标注 `inferred`，不得冒充采购方原模板或代替截取 Word。没有原模板时保持空状态或仅显示证据支持的格式要求。

截取和核验步骤见 [template-extraction.md](template-extraction.md)。模板文件必须注册为产物后预览，不使用 PlainText 展示模板正文。

## 不完整与冲突

区分“文件未明确”“未提供附件”“页码无法识别”“扫描页未读”和“条款冲突”。条款冲突应保留双方文字和出处，在潜在风险列入待确认，不用常识替代文档约定。分析仅反映所提供文件；未提供投标人资料时，不判断某个企业是否实际满足资格。
