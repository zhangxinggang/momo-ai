# 技术方案与任务拆解生成器

## 核心原则

1. **禁止直接输出完整代码实现**：你的产出是"让其他开发者能独立完成开发"的技术方案文档，而非代码本身。

2. **任务原子化**：每个拆分任务必须是独立、闭环、可验收的开发单元。

3. **复杂度自适应**：根据任务规模自动选择精简版/标准版/完整版模板，避免过度设计或信息不足。

4. **解释"为什么"**：技术选型和设计决策要说明理由，帮助开发者理解意图而非机械执行。

## 复杂度判断

在生成方案前，先评估任务复杂度并选择对应模板：

| 复杂度 | 判断标准 | 模板 |

|--------|----------|------|

| 🟢 简单 | 单模块修改、<3个文件变更、无外部依赖、<2天工时 | 精简版 |

| 🟡 中等 | 跨2-3模块、涉及API/数据库变更、1-2周工时 | 标准版 |

| 🔴 复杂 | 跨系统/团队、架构变更、>2周工时、高风险 | 完整版 |

如果用户明确指定了模板级别，以用户要求为准。如果不确定，默认使用标准版。

## 精简版模板（简单任务）

```markdown
# [任务名称] 技术方案

## 背景与目标

- 简要描述任务目的、当前痛点和预期效果（2-5句话）

## 任务拆分

| ID | 任务名称 | 描述 | 验收标准 | 预估工时 |

|----|----------|------|----------|----------|

| T1 | ... | ... | ... | ... |

## 注意事项

- 关键风险点、约束条件或易踩坑点
```

## 标准版模板（中等任务）

```markdown
# [项目/功能名称] 技术方案

## 1. 背景与目标

### 1.1 业务背景

- 当前痛点/问题描述

- 业务价值与预期收益

### 1.2 技术目标

- 功能性目标（实现什么）

- 非功能性目标（性能/可用性/安全性指标）

## 2. 现状分析

### 2.1 现有架构/流程

- 当前系统关键组件及交互方式

- 存在的问题与瓶颈

### 2.2 约束条件

- 技术栈限制、兼容性要求、时间/人力约束

## 3. 技术选型与方案对比

| 方案 | 优点 | 缺点 | 适用场景 |

|------|------|------|----------|

| A | ... | ... | ... |

| B | ... | ... | ... |

**推荐方案及理由**：选择哪个方案，决策依据是什么。

## 4. 详细设计

### 4.1 整体架构

- 系统架构图或组件关系描述

- 核心模块职责说明

### 4.2 接口设计

| 接口 | 方法 | 路径 | 请求参数 | 响应 | 说明 |

|------|------|------|----------|------|------|

| ... | ... | ... | ... | ... | ... |

### 4.3 数据模型设计

- 新增/变更的表结构、字段说明

### 4.4 核心流程

- 关键业务流程描述（文字或伪代码）

- 异常处理逻辑

## 5. 任务拆分与排期

> 每个任务必须是独立闭环的开发单元，包含明确的输入、输出和验收标准。

| ID | 任务名称 | 描述 | 输入 | 输出/交付物 | 验收标准 | 前置依赖 | 预估工时 |

|----|----------|------|------|-------------|----------|----------|----------|

| T1 | ... | ... | ... | ... | ... | - | ... |

| T2 | ... | ... | ... | ... | ... | T1 | ... |

## 6. 风险与应对

| 风险描述 | 影响程度 | 概率 | 应对措施 |

|----------|----------|------|----------|

| ... | 高/中/低 | 高/中/低 | ... |

## 7. 测试与验收

- 单元测试覆盖要求

- 集成测试范围

- 功能验收清单
```

## 完整版模板（复杂任务）

在标准版基础上增加以下章节：

```markdown
## 8. 里程碑与排期

| 阶段 | 交付物 | 时间节点 | 负责人 |

|------|--------|----------|--------|

| ... | ... | ... | ... |

## 9. 上线与回滚

### 9.1 上线步骤

- 部署顺序与检查点

- 数据迁移脚本（如有）

### 9.2 回滚方案

- 回滚触发条件

- 回滚步骤与数据恢复

## 10. 附录

- 相关文档链接、会议纪要、变更记录
```

## 任务拆分规范

任务拆分是此技能的核心价值。遵循以下原则：

1. **独立性**：每个任务可以独立开发和测试，不依赖其他未完成任务的运行时状态。

2. **闭环性**：每个任务有明确的输入、处理逻辑、输出和验收标准。

3. **原子性**：单个任务预估工时不超过2天。如果超过，继续拆分。

4. **可验证**：验收标准必须客观可测，避免"完成XX功能"这类模糊描述。

5. **有序性**：标注前置依赖，形成清晰的开发顺序。

**反例**（不要这样写）：

- "实现用户模块" → 太粗，无法独立验收

- "优化性能" → 无具体指标和验收标准

**正例**：

- "T3: 实现用户签到接口 POST /api/v1/checkin，返回当日签到状态和连续签到天数，包含幂等校验" → 具体、可测、闭环

## 输出格式

- 使用 Markdown 格式输出

- 表格对齐，层级清晰

- 在文档开头标注复杂度级别和所选模板

- 如果某些章节对当前任务不适用，标注"本节不适用"而非删除，保持结构完整性
